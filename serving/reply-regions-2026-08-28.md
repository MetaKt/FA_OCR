# ตอบกลับ — `regions` แก้แล้ว + สิ่งที่ต้องขอจากฝั่ง webapp

**วันที่:** 2026-08-28 · **จาก:** ทีมโมเดล · **ตอบเอกสาร:** `regions-required.md`
**สถานะ:** โค้ดแก้เสร็จ ผ่าน unit test แล้ว · **ยังไม่ deploy** รอยืนยัน 3 ข้อในหัวข้อ 3

---

## 1. สรุปใน 4 บรรทัด

1. แก้แล้วถึง **ระดับ 2** ตามตารางข้อ 4 ของคุณ — ทุก candidate มี `regions` ครบทุกหน้าที่บิลนั้นกิน และมีคีย์ `evidence`
2. **สาเหตุไม่ใช่ constrained decoding** ที่คุณสงสัยไว้ในข้อ 6.1 — เป็นเรื่อง contract drift ระหว่างสองฝั่ง อธิบายในหัวข้อ 2
3. เราคำนวณ "บิลนี้กินหน้าไหนบ้าง" ถูกมาตลอด แต่**ลบทิ้งก่อนส่งออก 1 บรรทัด** เพราะ validator ฝั่งคุณเป็น `additionalProperties: false`
4. ติดอยู่ 1 อย่าง: **ไฟล์ schema ใหม่ที่คุณอ้างถึงไม่ได้แนบมา** — มีแต่ `regions-required.md` รายละเอียดข้อ 3.1

---

## 2. สาเหตุที่แท้จริง — 3 ชั้น

### ชั้นที่ 1 — เราตัด `regions` และ `evidence` ทิ้งโดยตั้งใจ ไม่ใช่ decode หลุด

ในโค้ดเรามีบรรทัดนี้ (`src/stage2_extract.py`) ตั้งแต่ **2026-08-11**:

```python
DROPPED_FIELDS = ["regions", "evidence", "suggestedCategoryId",
                  "categorySuggestionReason", "categorySuggestionConfidence"]
```

วันนั้นเราตกลงกันว่าจะตัด `regions` ออก เหตุผลคือ Typhoon ไม่คืนพิกัดใดๆ กล่องที่เราส่งได้จึงเป็นกล่องเต็มหน้าเสมอ ซึ่งใช้ทำ click-to-highlight ไม่ได้ และฝั่ง FA ยืนยันว่าไม่ต้องการ — แล้วเราเพิ่ม `chunkPageIndex` เข้ามาแทนเป็นตัวชี้หน้า

**ฝั่งคุณไม่ได้อัปเดตไฟล์ schema ตามข้อตกลงนั้น** ไฟล์ที่คุณถืออยู่จึงยังบังคับ `regions` เป็น required มาตลอด นี่คือที่มาของความไม่ตรงกันทั้งหมด ไม่ใช่ว่า decoder ไม่เคารพ schema

เพิ่มเติมให้ชัด: **schema ที่โมเดล decode ตาม (`reduced_schema`) กับ schema ที่เราใช้ validate (`contract_schema`) เป็นคนละตัวกัน** โมเดลไม่เคยถูกขอพิกัดเลย เพราะมันมองไม่เห็นพิกัด ส่วน validator เราสร้างจากไฟล์ของคุณ *ลบ* คีย์ที่ตกลงกันว่าตัด — คำตอบเราจึงผ่าน validator ของเราเองทุกครั้ง ทั้งที่ไม่ผ่านของคุณ จุดที่คุณบอกให้ตรวจก่อนอย่างอื่นจึงไม่ใช่จุดที่พัง

### ชั้นที่ 2 — ข้อมูลหน้าถูกคำนวณถูกแล้ว แล้วถูกลบทิ้งก่อนส่ง 1 บรรทัด

`src/merge.py` เก็บหน้าทุกหน้าที่บิลหนึ่งกินไว้ในคีย์ภายในชื่อ `_pages` มาตลอด แล้ว `strip_internal()` ลบมันทิ้งก่อน response ออก — เพราะ validator ฝั่งคุณเป็น `additionalProperties: false` คีย์แปลกปลอมตัวเดียวทำให้ทั้ง chunk เป็นโมฆะ

แปลว่า **เรารู้อยู่แล้ว** ว่าบิลที่ 1 กินหน้า 0,1,2 และบิลที่ 2 กินหน้า 3,4 — แต่ส่งออกไปแค่ `chunkPageIndex` ซึ่งบอกหน้าแรกหน้าเดียว ตรงกับหลักฐานในข้อ 1 ของคุณเป๊ะ

### ชั้นที่ 3 — ใบหักภาษี ณ ที่จ่าย หายด้วยเส้นทางที่สอง

`src/certlink.py` จะรวมใบ 50 ทวิ เข้ากับใบเสร็จที่มันเป็นเจ้าของ (ย้ายเฉพาะ `withholdingTax` และ `withholdingTaxRate`) แล้ว**ลบ candidate ของใบรับรองทิ้งทั้งแถว โดยไม่บันทึกหน้าของมันไว้ที่ไหนเลย**

ดังนั้นต่อให้แก้ชั้นที่ 2 อย่างเดียว บรรทัด "ใบหักภาษี ณ ที่จ่ายที่เย็บติดกับใบเสร็จ … หายทุกใบ" ในตารางข้อ 2 ของคุณก็ยังจริงอยู่ ต้องแก้ทั้งสองที่

## 3. สิ่งที่แก้ไปแล้ว

เพิ่มโมดูลใหม่ `src/regions.py` เป็นเจ้าของเรื่อง "หน้าไหนเป็นของบิลไหน" ทั้งหมด **ไม่มีการเรียกโมเดลเลย** input เดิมให้ผลเดิมทุกครั้ง

| ทำอะไร | ที่ไหน |
| --- | --- |
| ทุก candidate มี `regions` ของหน้าตัวเองตั้งแต่เกิด | `stage2_extract.assemble` |
| บิลที่ merge ข้ามหน้า สะสมหน้าไว้ครบ | `merge.merge_pages` |
| ใบ 50 ทวิ ยกหน้าตัวเองให้ใบเสร็จก่อนถูกลบ | `certlink.apply_certificates` |
| หน้าที่ไม่มี candidate เลย ยกให้บิลที่อยู่ก่อนหน้า | `regions.attach_orphans` |
| สร้าง `regions` ใหม่จาก span จริง + ใส่ `evidence` | `regions.attach_regions` |
| เอา `regions`/`evidence` ออกจาก `DROPPED_FIELDS` | `stage2_extract.py` |

### 3.1 ผลลัพธ์ที่ได้จริง — เคส 5 หน้า 2 บิล ในข้อ 1 ของคุณ

```json
{"billCandidates": [
  {"candidateIndex": 0, "chunkPageIndex": 0,
   "regions": [{"chunkPageIndex": 0, "xMin": 0, "yMin": 0, "xMax": 1000, "yMax": 1000},
               {"chunkPageIndex": 1, "xMin": 0, "yMin": 0, "xMax": 1000, "yMax": 1000},
               {"chunkPageIndex": 2, "xMin": 0, "yMin": 0, "xMax": 1000, "yMax": 1000}],
   "evidence": []},
  {"candidateIndex": 1, "chunkPageIndex": 3,
   "regions": [{"chunkPageIndex": 3, "xMin": 0, "yMin": 0, "xMax": 1000, "yMax": 1000},
               {"chunkPageIndex": 4, "xMin": 0, "yMin": 0, "xMax": 1000, "yMax": 1000}],
   "evidence": []}
]}
```

คีย์อื่นเหมือนเดิมทุกตัว ไม่มีคีย์ใหม่นอก schema

### 3.2 ตรวจแล้วด้วยอะไรบ้าง

- `eval/test_regions.py` — **29 checks ผ่านหมด** synthetic ทั้งหมด ไม่ใช้ GPU ครอบคลุมข้อ 6.2 ทั้ง 3 ข้อของคุณ: ทุก candidate มี ≥ 1 region · `chunkPageIndex` ของตัวเองอยู่ใน `regions` ของตัวเอง · union ครอบคลุมทุกหน้าใน chunk
- `eval/test_merge.py` 26 ผ่าน · `eval/test_certlink.py` 37 ผ่าน — ไม่มี regression
- validate response จริงกับ **ไฟล์ schema ของคุณโดยตรง** (ตัวที่บังคับ `regions` required + `minItems: 1` + `additionalProperties: false`) → ผ่าน
- **ยังไม่ได้ยิงเข้า endpoint จริง** เพราะเครื่องกำลังถูกใช้ทดสอบอยู่ จะยิงก่อน deploy

## 4. ข้อที่ต้องขอ / ต้องยืนยัน

### 4.1 ขอไฟล์ — **บล็อกอยู่**

`regions-required.md` ข้อ 6.1 อ้างถึง `bill-extraction.schema.json` และ `sample-response.json` แต่**ไม่ได้แนบมา** ที่เราได้รับมีแค่ไฟล์ .md ไฟล์เดียว

สำคัญเพราะ server เราอ่าน schema ของคุณ **สดจากไฟล์** ที่พาธนี้:

```
C:\Users\meta_k\Downloads\adv-clear-model-handover\adv-clear-model-handover\bill-extraction.schema.json
```

ไฟล์ที่อยู่ตรงนั้นตอนนี้ลงวันที่ **2026-08-10** และ **ไม่มี `relatedDocumentNumber`** ถ้ามันเป็น required key ตัวที่ 32 จริง วินาทีที่ไฟล์ใหม่ถูกวางลงไป validation เราจะพังทันที ไม่เกี่ยวกับ `regions` เลย

**ขอ:** ส่ง `bill-extraction.schema.json` และ `sample-response.json` ตัวใหม่มา

**ถามต่อ:** `relatedDocumentNumber` คาดหวังค่าแบบไหน — wrapper `{value, confidence}` เหมือนฟิลด์ string อื่น และส่ง `{"value": null, "confidence": 0}` ได้เมื่อไม่มีข้อมูลใช่ไหม? ตอนนี้โมเดลยังไม่ได้อ่านฟิลด์นี้

### 4.2 ยืนยันกติกา "หน้าที่ไม่มีบิล"

ข้อ 6.2 ข้อ 3 ของคุณบอกว่า union ต้องครอบคลุมทุกหน้า แต่บางหน้าไม่ให้ candidate เลย — หน้าเปล่า หน้าลายเซ็น ใบส่งของที่เย็บตามหลัง เพราะ stage 2 หายอดเงินบนหน้านั้นไม่เจอ

**เราเลือก: ยกให้บิลที่อยู่ก่อนหน้าที่สุด** (หน้าที่อยู่ก่อนบิลแรกยกให้บิลแรก) เหตุผลคือเอกสารแนบมักตามหลังเอกสารที่มันสังกัด และผิดทางนี้ปลอดภัยกว่า — แนบเกินคือผู้ตรวจเห็นสแกนเกินมา 1 ใบ ส่วนไม่แนบคือหน้าหายไปเลย

**ยืนยันว่ารับได้ไหม?** ถ้าอยากได้แบบอื่น (เช่นทิ้งไม่ผูก แล้วให้ adapter ตัดสินเอง) บอกได้ แก้ที่เดียว

### 4.3 ยืนยัน: หน้าเดียวมี 2 บิล

ถ้าใบเสร็จ 2 ใบอยู่บนหน้าเดียวกัน ทั้งสอง candidate จะได้กล่องเต็มหน้าของหน้าเดียวกัน — **หน้าเดียวถูกอ้างโดย 2 บิล** schema ไม่ได้ห้าม แต่ข้อ 6.2 ของคุณพูดถึงแค่ "ครบทุกหน้า" ไม่ได้พูดถึงซ้ำ

adapter ฝั่งคุณรับได้ไหมที่สแกนหน้าเดียวกันโผล่ใต้บิล 2 ใบ? ถ้ารับไม่ได้ต้องคุยกัน เพราะถ้าไม่มีพิกัดจริงเราแยกครึ่งหน้าให้ไม่ได้

### 4.4 ยืนยันว่า `evidence: []` พอสำหรับรอบนี้

เราบอกได้ว่าบิลกินหน้าไหน แต่**ยังบอกไม่ได้ว่าแต่ละสแกนเป็น role ไหนใน 8 ค่า** ส่งอาเรย์ว่างตามข้อ 3.2 ที่คุณอนุญาต

ผลข้างเคียงที่คุณควรรู้: กฎการเงินที่ตัดสินจาก `evidence[].role` ในตารางข้อ 2 ของคุณ **จะยังทำงานไม่ได้** แม้แก้ `regions` แล้ว หน้าถูกผูกกับบิลถูกใบแล้วก็จริง แต่ไม่มีใครบอกว่าหน้าไหนคือสลิปโอน

ถ้าเรื่องนี้สำคัญ บอกมาว่าต้องการ role ไหนก่อน — `transfer_slip` กับ `receipt` น่าจะแยกได้ด้วยกฎ deterministic จาก transcript ไม่ต้องใช้โมเดลเพิ่ม แต่เป็นงานรอบถัดไป

### 4.5 `sourceRegions` — ขอข้ามรอบนี้

ตามข้อ 3.3 ที่คุณบอกว่าไม่บล็อก เราขอข้าม เพราะพิกัดรายฟิลด์ต้องมี localization จริง ซึ่งโมเดลปัจจุบันทำไม่ได้เลย ไม่ใช่ทำได้แต่ยังไม่ทำ

### 4.6 ขอ timeout ของ worker

deadline ฝั่งเราตอนนี้ **540 วินาที** ตั้งจากการเดา ขอตัวเลข lease จริงของ worker ฝั่งคุณ จะได้ตั้งเป็น lease ลบ 60 วินาที ไม่งั้นเราอาจกำลังทำงานต่อในงานที่ฝั่งคุณเลิกรอไปแล้ว

เวลาจริงที่วัดได้: **~50–72 วินาทีต่อหน้า** ขึ้นกับความหนาแน่นของเอกสาร chunk 5 หน้าที่คุณส่งมาใช้ **343 วินาที** ตรงกับที่เราวัดได้เอง (361 วินาที)

## 5. สิ่งที่เรา**ไม่**ทำ และเหตุผล

- **ไม่ส่งกล่องปลอมที่ดูเหมือนวัดมา** — ทุกกล่องคือ `0,0,1000,1000` เพราะนั่นคือความแม่นที่เรามีจริง กล่องแคบกว่านั้นจะเป็นการอ้างสิ่งที่เราไม่รู้
- **ไม่รวมหลายบิลเป็น candidate เดียว** ตามข้อ 7 ของคุณ — การตัดขอบเขตบิลไม่ถูกแตะเลย
- **ไม่เพิ่มคีย์นอก schema** — เราตรวจแล้วด้วยไฟล์ของคุณเอง
- **ไม่ให้โมเดลเดาพิกัด** — Typhoon ไม่คืนพิกัด การขอให้มันเดาคือการเชิญ hallucination เข้ามาในฟิลด์ที่ตรวจสอบไม่ได้
