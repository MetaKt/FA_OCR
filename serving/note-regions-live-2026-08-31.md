## 3. ที่แก้ตามเอกสารคุณ

### 3.1 deadline = 600 วินาที

ตั้งตามที่ขอ อยู่ใต้ client abort 660 s ของคุณ ไม่ใช่ใต้ lease — เหตุผลที่คุณให้มาถูก
และเป็นเหตุผลที่ดีกว่าที่เราใช้ตอนตั้ง 540

วัดล่าสุด **~56 วินาที/หน้า** chunk 7 หน้าอยู่ที่ ~390 s ยังมีระยะเหลือ

### 3.2 `relatedDocumentNumber`

ส่ง `{"value": null, "confidence": 0}` ตามที่ยืนยัน โมเดลยังไม่อ่านฟิลด์นี้

**แต่ส่งเฉพาะเมื่อไฟล์ schema ที่วางอยู่จริงประกาศคีย์นี้** เพราะถ้าส่งไปตอนที่เรายังถือไฟล์
2026-08-10 อยู่ จะโดน `additionalProperties: false` แล้วทั้ง chunk เป็นโมฆะ ส่วนถ้าไม่ส่งตอน
ไฟล์ใหม่มาถึงก็ fail validation เหมือนกัน เราจึงอ่านจากไฟล์แทนที่จะ hardcode ข้างใดข้างหนึ่ง

**ผลคือ: พอส่งไฟล์ schema มาแล้ววางทับได้เลย ไม่ต้องแก้โค้ด ไม่ต้อง restart** ฟิลด์จะโผล่เอง

## 4. ข้อ 1 ของคุณ — **ไม่ได้รับ `CHANGELOG.md` รอบที่ 3**

ตรวจบันทึกฝั่งเราแล้ว คำตอบคือ **ไม่ได้รับ** หรือได้รับไม่ครบ หลักฐาน 3 อย่าง:

1. **9 key ใหม่เราทำครบ** แต่บันทึกเราลงวันที่ **2026-08-17/18** ซึ่ง**ก่อน**เอกสารรอบที่ 3
   ของคุณ (2026-08-19) แปลว่ารายการ key เดินทางมาถึงเราคนละทางกับเอกสาร
2. **หัวข้อ "สองข้อที่ตัดออกไม่ได้" ไม่เคยมาถึง** บันทึกเรามีแต่ "regions ถูกตัด 2026-08-11"
   ไม่มีรายการโต้กลับ และกฎ `chunkPageIndex` ต้องอยู่ใน `regions` ก็ไม่มีในบันทึกเรา
3. **`payeeType` ฝั่งเรามี 2 ค่า ไม่ใช่ 3** — `["company", "individual"]` ไม่มี `shop`
   ซึ่ง `shop` อยู่ในรอบที่ 3 ข้อ 2 อย่างเดียว นี่คือหลักฐานที่ชัดที่สุด

ข้อ 3 คือของที่พังจริง ไม่ใช่แค่เรื่องเอกสาร: ถ้า ร้านค้า ถูกยัดรวมกับ `company`
ชุดหลักฐานของร้านค้าตามนโยบาย 88/2568 ก็หายไปหนึ่งชุด **จะแก้รอบหน้า** พร้อมกับ
`evidence[].role` เพราะทั้งคู่แตะตัวโมเดล ควรวัดความแม่นยำรอบเดียว

**ข้อเสนอเรื่องช่องทางส่ง** — ปัญหาไม่ใช่ความเห็นไม่ตรงกัน แต่เป็นไฟล์ไม่ถึง 2 รอบติด
(รอบที่ 3 และรอบนี้) ขอเป็นโฟลเดอร์กลางที่ทั้งสองฝั่งอ่านเขียนได้ — Drive, repo, อะไรก็ได้ —
เก็บ `bill-extraction.schema.json`, `sample-response.json`, `CHANGELOG.md` ไว้ที่เดียว
แล้วเราจะชี้ตัวอ่าน schema ไปที่โฟลเดอร์นั้นตรงๆ ถ้าคุณเปลี่ยน contract ระบบเราจะ fail
เสียงดังในรันถัดไป แทนที่จะเงียบๆ ตอบด้วย schema เก่าเหมือนที่เพิ่งเกิด

## 5. รอบหน้า — `evidence[].role` พร้อมข้อมูลจริง

ได้ตัวอย่างสลิปจริงจาก FA แล้ว (ชุด P06690 หน้า 192-197) เป็นภาพหน้าจอแอป K+ ทั้งหมด
จ่ายค่า M-Flow มีคำที่ใช้เป็นสัญญาณได้ชัดเจน: `จ่ายบิลสำเร็จ` · `เลขที่รายการ` ·
`ค่าธรรมเนียม` · `สแกนตรวจสอบสลิป` · `บันทึกช่วยจำ` · ชื่อธนาคาร

จะทำแบบเดียวกับ `certlink` คือกฎ deterministic อ่านจาก transcript ไม่เรียกโมเดลเพิ่ม
และ **ไม่มั่นใจ = ไม่ติด role** หน้าที่ไม่ติด role ผู้ตรวจติดเองเหมือนทุกวันนี้ ไม่แย่ลงกว่าเดิม

**คำถามที่ต้องการคำตอบก่อนเริ่ม:** rule engine ของคุณอ่านหน้าที่**ไม่มี** role ว่าอะไร?

- ถ้า "ไม่มีหน้าไหนเป็น `receipt`" ถูกอ่านว่า **"ไม่มีใบเสร็จ"** → การติด role บางหน้าจะ
  **แย่กว่าไม่ติดเลย** เพราะ `R-SLIP-001` จะเริ่มเตือนผิดกับเอกสารที่ปกติดี
- ถ้าอ่านว่า "ไม่รู้ ข้ามไป" → เราทยอยปล่อยได้ทีละ role

คำตอบข้อนี้ตัดสินว่าเราปล่อยทีละส่วนได้ หรือต้องรอทำครบก่อน

**อีกข้อ:** เอกสารไทยจำนวนมากพิมพ์หัวว่า **ใบเสร็จรับเงิน/ใบกำกับภาษี** พร้อมกันทั้งสองอย่าง
แต่ enum ให้เลือกได้ค่าเดียว ต้องการให้เป็นตัวไหน?

## 6. อีกเรื่องที่ FA เพิ่งชี้ให้เห็น — ตั๋วทางด่วนหลายใบในหน้าเดียว

ชุด P06690 หน้า 198 เป็นต้นไปเป็นใบรับค่าผ่านทางพิเศษ (EXAT) **หลายใบต่อหนึ่งหน้า**
และแต่ละใบถูก**ถ่ายสำเนาซ้ำในหน้าเดียวกัน** เพราะตัวตั๋วเองพิมพ์ว่า
*"กรุณาทำสำเนาเพื่อนำไปใช้ในธุรกรรมต่อไป"*

ตัวอย่างหน้า 200: มีตั๋ว 4 ภาพ แต่เป็นของจริง 2 ใบ (20.00 + 25.00 = 45.00)
อีก 2 ภาพคือสำเนาของสองใบนั้น — `Receipt Running No` กับ barcode ตรงกันเป๊ะ

กำลังดูอยู่ว่าฝั่งเราตอบยังไงกับหน้าพวกนี้ **ยังไม่แก้** จะรายงานตัวเลขก่อน
ถ้าจะแก้ ทางที่ปลอดภัยคือตัดซ้ำด้วย `Receipt Running No` ซึ่งเป็นเลขรันของตั๋วแต่ละใบ
ตั๋วสองภาพที่เลขเดียวกันคือใบเดียวกัน ไม่ใช่สองรายการ

ถ้าฝั่งคุณมีกติกาเรื่องนี้อยู่แล้ว (เช่น adapter ตัดซ้ำเอง หรือ FA คาดหวังให้เห็นทุกภาพ)
บอกมาก่อนจะได้ไม่ทำซ้อนกันสองที่
