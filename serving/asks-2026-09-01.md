# ขอ 4 อย่างจากฝั่งคุณ — เรียงตามผลกระทบ

**วันที่:** 2026-09-01 · **จาก:** ทีมโมเดล
**อ่านก่อน:** `note-regions-live-2026-08-31.md` · `toll-tickets-2026-08-31.md`

เอกสารนี้ไม่ใช่การปรึกษา เป็นรายการสิ่งที่**ต้องได้**เพื่อให้งานเดินต่อ
ของที่เราทำเองได้ เราทำไปแล้ว (ข้อ 5)

## 1. ส่ง `category` มากับ request — **สำคัญที่สุด**

ตอนนี้ `/v1/extract` รับแต่ไฟล์ PDF เปล่า ๆ **เราไม่รู้ว่า FA เลือกหมวดบัญชีอะไร**

เรามีกฎเฉพาะหมวดเขียนไว้ครบแล้วใน `data/category_rules.json` แต่**มันไม่เคยทำงานเลย**
เพราะไม่มีใครบอกหมวดมา นี่คือโค้ดที่ถูกต้องซึ่งตายอยู่เฉย ๆ

### ผลกระทบจริง วัดแล้ว

หมวด `5122100 ค่าแรง` จ่ายด้วย **ใบรับเงิน** ให้บุคคลธรรมดา
ยิง transcript ใบเดียวกันเข้า stage 2 สองแบบ (ค่าจริงตัดออกจากเอกสารนี้ เป็นข้อมูลส่วนบุคคล):

| ฟิลด์ | **ไม่ส่ง category** (เป็นอยู่ตอนนี้) | **ส่ง category** |
| --- | --- | --- |
| `sellerName` | `null` | ชื่อผู้รับเงินที่อ่านได้จริง |
| `sellerTaxId` | `null` | เลขบัตร 13 หลักที่อ่านได้จริง |
| `vat` | **`726.80`** ผิด | `null` ถูก |

สองอย่างที่พังโดยไม่ส่ง category:

1. **ไม่ได้ชื่อและเลขบัตรผู้รับเงินเลย** — ฟอร์มนี้ผู้รับเงินคือ "ผู้ขาย" แต่โมเดลไม่รู้
   ว่าต้องอ่านจากหัวข้อ *ข้อมูลผู้รับเงิน (บุคคลธรรมดา)*
2. **เอาภาษีหัก ณ ที่จ่ายไปใส่ช่อง VAT** — คนละภาษีกันคนละกฎหมาย ใบรับเงินไม่มี VAT เลย
   ตัวเลขนี้ถ้าหลุดไปถึงบัญชีคือรายงานภาษีผิด

### สิ่งที่ขอ

เพิ่ม **HTTP header เดียว** ไม่ต้องแก้ body ไม่ต้องแก้ contract:

```http
POST /v1/extract
Content-Type: application/pdf
Authorization: Bearer <token>
X-Category-Id: 5122100          ← ขอเพิ่มบรรทัดนี้
```

- **ตัวเลขล้วน ไม่ต้องมีขีด** — `5122100` ไม่ใช่ `5-122-100`
  (ส่งแบบมีขีดหรือมีชื่อไทยต่อท้ายก็ได้ ฝั่งเรา normalize ให้)
- **ไม่ส่งก็ได้** — ถ้าไม่มี header นี้ ระบบทำงานเหมือนเดิมเป๊ะ **ไม่ใช่ breaking change**
  คุณจะ deploy เมื่อไหร่ก็ได้ ไม่ต้องรอกัน
- ฝั่งเรารองรับรอไว้แล้ว รอแค่ค่าที่ส่งมา

**FA เลือกหมวดก่อนอัปโหลดอยู่แล้ว** ข้อมูลนี้มีอยู่ในมือคุณแล้ว แค่ยังไม่ได้ส่งต่อ

## 3. เอา `confidence` ไปแสดงผลด้วย

ตั้งแต่วันนี้ ถ้าตัวเลขบนบิล**คำนวณไม่ลงตัว** เราจะ**ลด `confidence` ของฟิลด์นั้นเหลือ `0.3`**

เราจะ **ไม่แก้ตัวเลขให้** เพราะสมการที่ไม่ลงตัวบอกว่า "ชุดนี้ผิด" ไม่ได้บอกว่า "ตัวไหนผิด"
เดาแล้วแก้เอง = ส่งเลขผิดที่ดูน่าเชื่อไปให้ผู้ตรวจ ซึ่งแย่กว่าเลขผิดที่ติดธง

**สัญญาณนี้จะไร้ค่าทันทีถ้าหน้าจอไม่แสดงมัน**

ขอให้ฝั่ง webapp ทำอย่างใดอย่างหนึ่ง:
- ไฮไลต์ช่องที่ `confidence <= 0.3` ให้ผู้ตรวจเห็น หรือ
- เรียงรายการให้บิลที่มีช่อง confidence ต่ำขึ้นก่อน

**ยืนยันกลับมาว่าตอนนี้ webapp ใช้ `confidence` ทำอะไรอยู่หรือเปล่า** ถ้าไม่ได้ใช้เลย บอกมา
จะได้หาวิธีส่งสัญญาณทางอื่น

## 4. คำถาม 3 ข้อที่ยังไม่ได้คำตอบ

### 4.1 rule engine อ่านหน้าที่**ไม่มี** `role` ว่าอะไร

- ถ้า "ไม่มีหน้าไหนเป็น `receipt`" ถูกอ่านว่า **"ไม่มีใบเสร็จ"** → การติด role บางหน้าจะ
  **แย่กว่าไม่ติดเลย** เพราะ `R-SLIP-001` จะเริ่มเตือนผิดกับเอกสารที่ปกติดี
- ถ้าอ่านว่า **"ไม่รู้ ข้ามไป"** → เราทยอยปล่อยทีละ role ได้

**คำตอบข้อนี้ตัดสินว่าเราเริ่มทำ `evidence[].role` ได้เลย หรือต้องรอทำครบก่อน**

### 4.2 เอกสารที่พิมพ์หัวว่า **ใบเสร็จรับเงิน/ใบกำกับภาษี** พร้อมกัน — เอา role ตัวไหน

### 4.3 ตั๋วทางด่วนที่รวมเป็นแถวเดียว — ขอคำตอบจาก FA 3 ข้อ (รายละเอียดใน `toll-tickets-2026-08-31.md` ข้อ 5)

1. `documentDate` = null / วันแรกสุด / วันหลังสุด
2. `amountBeforeVat` กับ `vat` เป็น null ได้ไหม (ตั๋วปน VAT กับ Non-VAT)
3. `originalDocumentNumber` = null ได้ไหม (เลขตั๋วเก็บใน `lineItems`)

**และยืนยัน:** ฝั่งคุณตัดซ้ำระดับไฟล์อยู่แล้วใช่ไหม ต้องการ key รายใบเพิ่มไหม

## 5. ที่เราทำเสร็จแล้ววันนี้ — ไม่ต้องทำอะไร แค่รับทราบ

### 5.1 ตัวจับ OCR วนซ้ำ + อ่านหน้าใหม่ · **ขึ้นแล้ว**

ตั๋วทางด่วนหน้า 198 เคยได้ 0 candidate ตอนนี้ได้ 2 · **ได้เงินคืน 75 บาท (190 → 265)**
ยิงซ้ำ 5 รอบ ได้ 265 ทุกรอบ ต่างกัน 0.00 · จับลูปได้ 5/5 · ไม่กระทบไฟล์ที่เคยถูกอยู่แล้ว

ยังเหลือ 45 บาทที่อ่านไม่ออก เป็นตั๋วแบบเจาะรู **อ่านไม่ออกทุกความละเอียดที่ลอง** (ดู `toll-tickets`)

### 5.2 ตัวตรวจการคำนวณเงิน · **ขึ้นแล้ว**

บิลไทยบอกตัวเลขมากกว่าที่จำเป็น ส่วนเกินนั้นใช้จับ OCR อ่านเลขผิดได้ฟรี ๆ:

```
amountBeforeVat + vat = originalTotal
vat             = amountBeforeVat x 7%          ไทยมีอัตราเดียว
withholdingTax  = amountBeforeVat x หนึ่งใน 1 / 1.5 / 2 / 3 / 5 / 10 / 15%
```

จับได้จริงแล้ว 2 เคส:

- **ใบรับเงิน** — OCR อ่านยอดรวมเป็น `24,826.80` ของจริงคือ `24,226.80`
  จับได้เพราะ `726.80 / 24,826.80 = 2.93%` **ไม่ใช่อัตราที่มีอยู่ในกฎหมายไทย**
  ส่วน `726.80 / 24,226.80 = 3.00%` พอดี · ตัวเลขนี้มองด้วยตาไม่มีทางรู้ว่าผิด
- **ตั๋วทางด่วนหน้า 201** — `vat 80.00` บนฐาน `35.00` คือ 228% เคสที่เราเคยเขียนว่า
  "ยอดถูก ช่องผิด" ตอนนี้ระบบจับเองแล้ว

ทดสอบกับ candidate จริง 16 ใบจาก response ที่เก็บไว้ทุกไฟล์ → **เตือนผิด 0 ครั้ง**
ต้นทุน **8.8 ไมโครวินาที** ต่อ chunk ไม่เรียกโมเดล ไม่มีผลต่อความเร็ว

### 5.3 กำลังจะทำต่อ — ชุดเอกสารหมวดค่าแรง

ใบรับเงิน + สำเนาบัตรประชาชน + สลิปโอนเงิน ต้องมัดเป็นบิลใบเดียว
รูปแบบเดียวกับที่ทำ `certlink` (ใบเสร็จ + หนังสือรับรองหักภาษี) และ `regions` (บิลหลายหน้า)
กลไกรวมหน้ามีอยู่แล้วใช้ซ้ำได้เลย

**ต้องได้ข้อ 1 (category) ก่อน** ไม่งั้นชื่อกับเลขบัตรผู้รับเงินยังเป็น null อยู่ดี
