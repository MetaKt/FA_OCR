# ส่วนที่ 1 — ถึงคนทำ webapp

## 1.1 ยืนยัน 3 ตัวเลขนี้ก่อนเราสั่งเครื่อง — **สำคัญที่สุด**

`README.md` ของคุณเป็นสัญญาฉบับแรก และ**บางส่วนเก่าไปแล้ว** — มันยังขอภาษาลาวกับความแม่น 95%
ซึ่งทั้งสองอย่างยกเลิกไปแล้ว ปัญหาคือเราแยกไม่ออกว่าบรรทัดไหนยังใช้อยู่

| สิ่งที่ README เขียนไว้ | สถานะ |
| --- | --- |
| worker lease 5 นาที | **ยกเลิกแล้ว → 900 วิ** ยืนยัน 2026-08-28 |
| client abort | **660 วิ** ยืนยัน 2026-08-28 (เราตั้ง deadline 600 วิ ให้ต่ำกว่า) |
| chunk ≤ 40 MB / 40 หน้า | **ยังไม่ยืนยัน** |
| 300 หน้าต่อ job | **ยังไม่ยืนยัน** |
| ทำพร้อมกัน 5 job | **ยังไม่ยืนยัน** ของเราตอนนี้ = 1 |

**ที่ต้องการ:** ยืนยันหรือแก้ 3 บรรทัดล่าง

**ทำไมถึงสำคัญ:** เราวัดความเร็วจริงแล้ว — **57.1 วินาทีต่อหน้า** บนโน้ตบุ๊กเครื่องนี้
(RTX 5060 Laptop, 8 GB) วัดจาก 12 หน้าจริง เสถียร 56.4 / 57.3 / 58.0

```
10 หน้า =  571 วิ   พอดี deadline 600 วิ
20 หน้า = 1143 วิ   ต้องรัน 2 สายพร้อมกัน
40 หน้า = 2285 วิ   ต้องรัน 4 สายพร้อมกัน
40 หน้า × 5 job     ต้องรัน ~20 สายพร้อมกัน
```

**หนึ่งสายกินแรม GPU 5.3 GB จากที่มี 8.1 GB** สองสายต้องการ ~10.7 GB — คือ**ใส่ไม่ได้จริง ๆ**
ไม่ใช่ช้า ไม่มีการแก้ซอฟต์แวร์ใดช่วยได้ ต้องเปลี่ยนเครื่อง

คำตอบของคุณเปลี่ยนสเปกเครื่องที่จะซื้อจาก "ที่มีอยู่ก็พอ" ไปจนถึง "ต้องการการ์ดระดับ datacenter สองใบ"
เราจึงยังไม่เขียนสเปกจนกว่าจะได้คำตอบ

## 1.2 ไฟล์ schema — ขอรอบที่ 4

`bill-extraction.schema.json` กับ `sample-response.json` ที่ generate ใหม่ **ยังไม่เคยมาถึงเรา**
ไฟล์ที่เราถืออยู่ลงวันที่ **2026-08-10**

ผลที่ตามมาตอนนี้:

- ไฟล์นั้นประกาศ **22 key จาก 31 key** ที่ตกลงกัน เราจึงต้องเติมส่วนที่ขาดเองในโค้ด
- ยังไม่ประกาศ `withholding_certificate` ที่ตกลงกันไว้ 2026-09-02 **เราตรวจเจอหน้า 50 ทวิ
  แล้วแต่ยังไม่ใส่ค่านั้นลงไป** เพราะถ้าใส่ค่าที่ schema ไม่ประกาศ validation จะไม่ผ่าน
  แล้ว**ทั้ง chunk จะตกทั้งก้อน** ไม่ใช่แค่ฟิลด์เดียว
- ไฟล์นั้นไม่ประกาศ `payeeType` เลย

พอไฟล์มาถึง ค่านั้นจะโผล่ขึ้นมาเองทันที ไม่ต้องแก้โค้ด

**ขอเสนออีกครั้ง:** วางไฟล์ไว้ในโฟลเดอร์กลางที่อ่านเขียนได้ทั้งสองฝั่ง (Drive / repo / อะไรก็ได้)
แล้วเราชี้ตัวอ่าน schema ไปที่นั่นตรง ๆ ถ้า contract เปลี่ยน ระบบเราจะ fail เสียงดังในรันถัดไป
แทนที่จะเงียบ ๆ ตอบด้วย schema เก่า — ซึ่งเป็นสิ่งที่เพิ่งเกิดไปแล้ว 2 รอบ

# ส่วนที่ 2 — ถึง FA

## 2.1 ค่าผ่านทางที่รวมเป็นบรรทัดเดียว — ขอ 3 คำตอบ

ตั๋วทางด่วนของทริปเดียวกันหลายใบ ตอนนี้เรารวมให้เป็น **1 บรรทัดในบัญชี** แล้ว
(เฉพาะหมวด `5223100 ค่าเดินทาง ในประเทศ`) และตัดใบที่เป็นสำเนาซ้ำออกอัตโนมัติ

แต่พอรวมหลายใบเป็นใบเดียว มี 3 ช่องที่**เราเดาแทน FA ไม่ได้** ตอนนี้ใส่ค่า default ไว้ก่อน
ถ้า FA ตอบมา แก้ที่ละจุดเดียวจบ:

| ช่อง | ตอนนี้ใส่อะไรไว้ | ทำไมถึงต้องถาม |
| --- | --- | --- |
| `documentDate` | วันที่ของ**ตั๋วใบแรกสุด** | ตั๋วในแผ่นเดียวกันคนละวันกันได้ เคยเจอ 13/07 กับ 20/07 อยู่ในชุดเดียวกัน |
| `vat` / `amountBeforeVat` / `vatRate` | **ว่าง (null)** | ในชุดเดียวกันมีทั้งตั๋ว `Baht(Vat Included)` และ `Baht(Non Vat)` ปนกัน แยกยอดแบบเดียวให้ตรงทุกใบไม่ได้ |
| `originalDocumentNumber` | **ว่าง (null)** แต่เก็บเลขที่ทุกใบไว้ใน `lineItems` | ใบที่รวมแล้วไม่มีเลขที่ของตัวเอง |

**คำถาม:** 3 ค่านี้ FA อยากให้เป็นอะไร

## 2.2 FA ยื่น **ภ.ง.ด.54** ไหม

`payeeType` ของเรามี 2 ค่า: `company` (นิติบุคคล → ภ.ง.ด.53) กับ `individual` (บุคคลธรรมดา → ภ.ง.ด.3)
สองค่านี้ครอบคลุมทุกกรณีในประเทศ

แต่ในชุดเอกสารจริงมีผู้ขาย**ต่างประเทศ** เช่น Agoda (จดทะเบียนสิงคโปร์) และ Trip.com
ตอนนี้เราตอบว่า `company` ซึ่งถูกตามชนิดผู้รับเงิน

**คำถาม:** FA ต้องยื่น **ภ.ง.ด.54** สำหรับการจ่ายไปต่างประเทศในชุดเคลียร์เงินทดรองด้วยหรือเปล่า

- **ถ้าไม่ต้อง** — จบ ไม่ต้องทำอะไรเพิ่ม
- **ถ้าต้อง** — เราจะทำสัญญาณแยกอีกตัวว่า "ผู้รับเงินอยู่ต่างประเทศ" ไม่ใช่เพิ่มค่าใน `payeeType`
  เพราะ ภ.ง.ด.54 ตัดสินจาก**ถิ่นที่อยู่** ไม่ใช่จากชนิดผู้รับเงิน และเราดูออกอยู่แล้วจากการที่
  ไม่มีเลขผู้เสียภาษีไทย 13 หลักที่ผ่านการตรวจ check digit
